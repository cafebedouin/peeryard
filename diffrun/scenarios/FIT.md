# Which scenario fits which change

A pull request's production footprint (`diffrun/build.sh --dry-run <base> master...pr-N -- src/main
ergo-core/src/main ergo-wallet/src/main avldb/src/main` lists the files) tells you which scenario, if any,
can observe its effect. This table is the fit; it is a starting point, not a rule.

| touched paths (ergoplatform/ergo) | what the change can affect | scenario | what it observes |
|---|---|---|---|
| `src/main/scala/org/ergoplatform/network/ErgoNodeViewSynchronizer*`, `.../network/**`, `scorex/core/network/**` | sync negotiation, header and block download, peer handling | `fork-convergence` | does a follower on a lighter static fork switch to a heavier fork it meets |
| `.../nodeView/history/storage/modifierprocessors/{FullBlockProcessor,HeadersProcessor,ToDownloadProcessor}*`, `.../nodeView/history/**` | best-chain choice, block-section application, download scheduling (a change to `ToDownloadProcessor`'s lookback thresholds, 100 near the tip and 128 far behind, is reached by no shipped scenario: revert check plus a read, not a smoke) | `sibling-fork` (and `regression/` #525 spec) | best full block vs best header on different forks at one height; agreement after delayed dual mining |
| `.../nodeView/history/**` with reorg or rollback logic, `.../nodeView/state/**` | rollback and re-application | `fork-convergence` (a switch is a rollback) | switched, margin, rollbacks in the node log |
| `.../mining/**`, `.../settings/**` (chain parameters) | block production, difficulty | rig `soak` (rate across the retarget), `mining` | block rate, retarget, quiescence |
| `.../nodeView/mempool/**`, `.../nodeView/wallet/**`, `.../modifiers/mempool/**` | transaction validation, relay, wallet | `txload` | payments accepted, confirmed, counted in blocks, on each jar |
| `.../nodeView/wallet/**`, `ergo-wallet/src/main/**`, wallet persistence, rescan, rollback or start-up code | whether the wallet's view (addresses, balances, unspent boxes, transactions, scans) survives a lifecycle event | diffrun `wallet-oracle-restart` (`WO_EVENTS`: `restart`, `crash`, `rescan`; `WO_AT=confirmed` or `pending`) and `wallet-oracle-fork` (`WO_EVENTS=fork`: a rollback; needs netem), base and candidate each on its own jar (`pr-scenario.yml`, `scenario_env` for the parameters); the rig examples of the same names for one jar by hand, with their A/A (`none`) and positive control (`rescan-from`, must FAIL) | the subject's wallet against a reference wallet with the same keys that went through nothing, field by field at a settled point (`rig/WALLET-ORACLE.md`); within a run the oracle needs no second jar, so base against candidate shows whether the change removes (or adds) a DIFF |
| `.../nodeView/wallet/**`, `ergo-wallet/src/main/**`, `.../http/api/{Wallet,Scan,Transactions}ApiRoute*`, `.../nodeView/mempool/**` | wallet box selection, transaction building (issue, burn), scans, fee estimation, mempool conflict handling | `wallet-workload` (`-plain` for the sequential steps only) | per step: inputs never shared by accepted sends, token id = first input, exactly the burned amount gone, no scan-only box spent, fee answers monotone, a resubmitted or conflicting spend confirmed once everywhere and gone from every pool, one state root across both versions |
| `.../nodeView/state/**Snapshot**`, `.../modifierprocessors/UtxoSetSnapshotProcessor*`, `.../state/DigestState*` | UTXO-set snapshot bootstrap, digest state across restart | `bootstrap-modes` (one pair, no smoke manifest needed; digest and pruned followers), plus the node's own `*SnapshotProcessorSpecification`/`*NetworkSpecification` through the revert check | followers settle on the same state root; the added specs guard the change | no diffrun scenario stages `utxoBootstrap`; the rig example `utxo-bootstrap` does (convert it through `lib/rig-scenario.sh` when the PR's question is the bootstrap itself) |
| `.../nodeView/history/extra/**` (the extra indexer), `.../http/api/BlockchainApiRoute*` | what `/blockchain/...` serves with `extraIndex` on | `indexer-diff` (both jars on one chain, two indexers compared) | every indexed box and transaction, per-address balance, transaction and box ids, unspent boxes, token info, at settled points after payments, a restart and a rollback |
| `.../nodeView/history/**` (history storage, repair after a partial write), `.../nodeView/state/**` (state recovery at startup, `restoreConsistentState`), `.../nodeView/ErgoNodeViewHolder*`, `avldb/**` | what a node restores from disk after it is killed mid-write: history and state left out of step, objects stored without their index, recovery that fails or exposes a half-written object | `crash-consistency` (one pair; `CC_ROLE` digest / pruned / miner for other node roles, `CC_INDEXER=1` with `CC_KILL_ON=indexed` for `.../history/extra/**`) | after 3-5 SIGKILLs inside block bursts and restarts, S agrees with an untouched follower and the miner by best full block and state root (and indexer answers); SAME / DIFF / LOGERR / STUCK / REFUSED. Applies to: ergoplatform/ergo#2675, #2541, #2523, #2548 |
| `.../http/api/**` | REST only | none; the scenarios poll `/info` and `/blocks/at`, so an API change can VOID runs (versions) or break polling, which shows as INCONCLUSIVE | — |
| `src/it/**`, `src/test/**`, docs | tests and docs only | none (nothing to compare on a network) | — |
| `.../mining/CandidateGenerator*`, `.../mining/StorageRentClaimBuilder*`, storage-rent rules in `ErgoInterpreter`/`ErgoTransaction` | storage-rent claims a miner puts into its own blocks; their acceptance by other versions | `storage-rent-2598` (needs jars with `patches/test/`: storage period 60, `txRentDistinctOutputs` from height 30) | claims in the chain checked against the rule from the blocks, holder boxes claimed, a base-jar and a candidate-jar follower on the miner's state root |
| protocol version, voting, soft-fork activation, sync between versions | two versions on one network | `interop` (release and candidate on one network, each mining in turn); the activation scenario itself does not exist yet | same chain and state root in both directions |

A mempool change that alters *which* transactions are kept (conflict cleanup, eviction, re-validation) is answered by
the revert check on its spec plus a read of the pool path; `txload` only shows the benign payment path still works.
A conflict needs two valid spends of one box; the honest form (one wallet on two nodes, each paying from the same box)
is `wallet-workload`'s `conflict` step (`WW_PRESET=conflict` runs only the resubmit and conflict steps).

If no row fits, say so in the review instead of running the nearest scenario: a verdict on the wrong scenario
is evidence about nothing.
